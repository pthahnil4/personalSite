一条 HTTP/2 长连接，卡了我三天

批量做多周期趋势分析时，请求跑着跑着就开始失败，日志里只有一行 获取K线异常:，冒号后面什么都没有。空的报错比报错本身更难办， 因为你连是超时、是断连、还是参数被拒都不知道。

现象：报错信息是空的

抓下来看，异常对象是传输层的，消息体为空。翻译成能听懂的话就是： 连接被对端关掉了，而 SDK 把这件事原样抛了上来，没有补任何上下文。

  • 失败是成批出现的，一次请求失败后面几个都失败——像是共用同一条连接。
  • 手工单发一次请求总是好的，说明不是参数或权限问题。
  • 失败集中在长时间空闲之后第一次调用，像是连接已经死了但客户端不知道。

「异常消息为空」不是没信息，它本身就是信息：错误发生在比业务层更下面的地方。

我一开始的错误方向

前两天的做法都是错的：加重试、加 sleep、把 SDK 换成手写请求。 手写请求那次甚至看起来「修好了」——因为我顺手把连接改成了每次新建。 它掩盖了真正的问题：高频重建连接反而让情况更糟。 

# 错的做法：每次调用都新建客户端实例
for sym in symbols:
    api = MarketAPI(instType="SWAP")   # 连接重建，代价是握手与断连
    data = api.get_candlesticks(inst_id=sym, bar=bar)

# 对的做法：实例复用，显式设超时，失败时按连接级错误重建一次
api = MarketAPI(instType="SWAP")       # 进程内长驻
api.timeout = 15                        # 没有超时，卡死会一直占着调度
data = fetch_with_rebuild(api, sym, bar)

代码块示例：左边注释标出错误方向，右边是最后留下的写法。

三件真正起作用的事

动作 解决什么
给行情实例设显式超时 不再出现「整批请求卡住不动」，失败能在秒级暴露
把实例改成进程内复用 消除高频连接重建，断连频率显著下降
识别为连接级错误时才重建，且只重建一次 避免把参数错误当断连处理，也避免雪崩式反复重建

顺序很关键：先分类错误，再决定要不要重建连接。 一见到异常就重建，等于把所有 bug 都当成网络问题。

留下的规矩

  1. 任何对外请求都必须有显式超时，默认值不可信。
  2. 批量接口按串行执行，别依赖会共享的全局适配器状态。
  3. 报错信息为空时，日志里要自己补上「哪个币、哪个周期、第几次重试」。
  4. 连续失败要升级成告警，而不是继续默默重试到第二天。

如果只记一条

传输层错误和业务错误必须分开处理。混在一起重试， 会把一个能在十秒内定位的问题拖成三天。
