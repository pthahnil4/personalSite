把三个市场并成一个应用，分七步走

手头有两个 Flask 应用：一个跑 OKX 永续的实盘监控与下单，另一个跑国内期货和股票。 各自一套模板、一套导航、一套部署脚本，还都叫「监控台」。 并到一起这件事我拖了两周，因为直觉上觉得「能跑就别动」。

为什么不继续两套并行

真正的成本不是代码重复，是心智要分两份。同一个策略思路要在两个仓库里 各写一遍，改一处指标口径得记着改两处，服务器上要留两个端口、两套进程守护、 两套备份路径。加上第三个模块（K 线训练）准备进来，我算了一下： 再并行下去，第四套一定会出现。

  • 被并入的那一侧没有版本仓库，改错了没有回退点。
  • 两侧的解释器环境不一致，一边能跑另一边缺依赖。
  • 策略层已经有一半是共用的，继续分开只是把耦合藏起来。

合并的收益要能立刻兑现，否则就别合并。我把这条写在方案第一行， 用来挡住「顺手重构一下」的冲动。

冲突全景：谁覆盖谁

动手前先把会撞的地方列全，因为合并事故几乎都不是「报错」， 而是静默地用了错的那一份。

撞车点 表现形式 处理
同名模块 import task 导进来的不是当前模块，表现为莫名其妙的密钥错误 显式设置搜索路径顺序，包名带上下级目录
模板遮蔽 两侧都有 index.html，页面显示的是另一套的内容 模板按模块加前缀目录，逐页复验
静态资源 同名 CSS 互相覆盖，改样式不生效 公共样式合一，模块样式独立文件
数据目录 硬编码路径，换机器就找不到数据 外置路径自动识别，数据与代码隔离
依赖清单 一侧多装了冗余包，另一侧缺关键包 合并后重新对齐清单，删掉不再用的
凭据 明文密钥散落在几个脚本里，其中一处会随仓库公开 统一走一处配置，复扫并核对

七个阶段，每步都能回退

每个阶段的定义是：改完能独立验收，出问题能独立回退。 这条约束比「分得细」更重要——它决定了我敢不敢在实盘跑着的时候动手。 

Phase 0  基线与快照      —— 先把能跑的状态固定下来，没有仓库的先建仓库
Phase 1  公共策略层      —— 两套共用的指标与判定先并成一份
Phase 2  期货模块并入    —— 监控台、星标行情、多周期三页
Phase 3  股票模块并入    —— 依赖 Phase 2 的目录约定
Phase 4  K 线训练并入    —— 主战场：账号体系与榜单要对齐
Phase 5  配置、密钥、依赖收口
Phase 6  部署入口与前端收口 —— 单实例守护、模板遮蔽、降级提示
Phase 7  文档归档与模块边界收口

阶段清单：前四步搬功能，后三步收边界。后三步看起来没内容，出事最多。

Phase 4 花的时间最长，因为 K 线训练带自己的账号概念，而主应用原来的假设是 「这是我自己用的控制台」。两种用户模型撞在一起时， 我选择把训练侧的账号做成独立子系统，而不是硬套主应用的结构。

两个反直觉的结论

1. 导航不会自动长出新入口

导航改成数据驱动之后，我以为新模块并进来，页面入口会自己出现。 实际不会：只要用户保存过自定义配置，读的就是那份配置， 新增的内置入口必须手动添加一次。验收口径因此改成两句 ——「新库自带」和「老库需手动加」，不能混着说。

2. 冒烟全绿证明不了判定逻辑是对的

改完一个依赖外部数据的判定条件后，页面能开、接口有返回、没有报错。 但那些结果只能证明它跑起来了，证明不了它判得对。 后来定了条规矩：改判定逻辑，就拿生产真实数据做一次前后对照。

留下的规矩

  1. 合并前先给没有仓库的一侧建仓库，回退点比效率重要。
  2. 同名模块、同名模板要当成缺陷登记，不能靠记忆避开。
  3. 阶段拆分标准是「能独立验收 + 能独立回退」，不是工作量。
  4. 后三步（依赖、凭据、文档）单独占提交，混进功能里就等于没做。
  5. 改了判定逻辑，就用真实数据对照一次，别用冒烟结果代替。

如果只记一条

合并的风险不在被搬的代码里，在两边都以为「这份是我的」的那些文件上： 模块名、模板名、数据路径、凭据。
